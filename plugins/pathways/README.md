# pathways plugin

`/pathways` in Claude Code opens the Pathways tool on this laptop: a standalone copy that runs from this plugin, from any folder. No repo, and nothing to install by hand: on the first run, `start.sh` downloads pinned builds of Node and cloudflared into the plugin's data folder (checking each against its SHA-256), and asks macOS to install Apple's developer tools (git and Python) if they're missing. Analyse runs Claude Code on the person's plan: `claude` on PATH or from Anthropic's installer, or else the copy inside the Claude desktop app, so desktop-only people need nothing more. Its working folder is `~/Downloads/Pathways`, or `PATHWAYS_WORKSPACE` if that's set.

It starts empty, with no sample data. **Fetch latest** in Documents signs you in to Cloudflare Access (cloudflared opens your browser: emailed code, then authenticator) and downloads every document that isn't archived from the admin Worker into `documents/` in the working folder, checking each against its SHA-256. The Worker logs every download. The sign-in token stays with cloudflared and the tool's server; it never reaches the page.

Fetch latest also brings down three settings records a person saves once: the industries and markets (`push-structure <structure.json>`), which sources are licensed, so the map can label them (`push-sources <internal-sources.json>`), and the context factors (`push-factors <context-factors.json>`). Run them through the starter, which brings its own Node and cloudflared: `sh start.sh "$HOME/Library/Application Support/Pathways" push-sources <file>`, with the file outside any git repo. The sources' names live only in Cloudflare, since this plugin is public; without them, documents are labelled licensed by their `licensed-` id only. **Add files** uploads through the Worker (confidentiality first; the checkout is taken if free and given back after).

**The dev bucket** holds the team's whole working folder, so another laptop can pick up the work: `push-dev [folder]` sends its `landscape/`, `sources/` and `client/` through the Worker (only files the bucket doesn't hold yet, then a snapshot of every path; the checkout is taken if free and given back after), `dev-snapshots` lists the snapshots, and `pull-dev [folder] [snapshot] [--all]` brings the latest one (or the one named) down into a folder outside git, checking every file. A pull is light by default: `landscape/` and `client/` without the original documents and images, and no `sources/`, so about 100 MB rather than the whole library; `--all` brings everything. Downloads run eight at a time. A note in the folder (`.pathways-dev.json`) records the snapshot it is in step with: a newer pull updates files unchanged since, removes those the snapshot no longer has, and stops before writing if one was changed here; files never synced are left alone. A push from a light folder keeps the originals it never held, and is refused while dev has a newer snapshot: pull first. A folder with no note pushes only with `--first`, when it holds the whole library. Nothing in the bucket is ever deleted. `restore-dev <snapshot>` rolls dev back: it records that earlier snapshot again as the newest (nothing is downloaded or sent, and the snapshots in between stay, so a restore can be undone the same way); everyone then pulls. Links, `.DS_Store`, `.git/`, `node_modules/` and SQLite's scratch files are never sent. The folder defaults to the working folder.

**Analyse and extract** rereads every document that isn't archived: it turns each into text parts (PDF through macOS's own PDF framework, Word and HTML through `textutil`), starts a headless Claude Code session on the person's plan to read every part against `landscape/extraction-brief.md`, then runs the build (`merge`, `check`, `map`). That session reads documents that came from outside, so it's fenced in: it reads only inside the working folder and writes only its output and scratch folders (its subagents too), with Claude Code's own memory, plan and temporary folders denied and auto memory off; it has no shell, no web and no MCP servers; it loads no settings, hooks or CLAUDE.md, the person's or any planted in the folder; it's told that document text is data, never instructions; and it runs with API-key variables removed. The fence was tested on Claude Code 2.1.49. Stop ends it; a stopped or failed run leaves the previous results as they were. Its log and the build's are in `landscape/evidence/runs/current/`.

## Install

Once per person. The Claude desktop app can't add a marketplace (no `/plugin marketplace add`, no button), so the person pastes a message asking Claude to run the CLI that ships inside the app; the public repo's README has the exact wording (`apps/ui/release/README.md`). In a terminal, with a current Claude Code, it's:

```bash
claude plugin install pathways --marketplace Parallel-intelligence/pathways-plugin
```

Then `/pathways` in a new chat. It clones over public HTTPS, so it needs git (Apple's developer tools) but no GitHub account. Updates: `claude plugin marketplace update pathways && claude plugin update pathways@pathways`, then a new chat. If you added the team's earlier marketplace (the cms repo, also named `pathways`), remove it first with `claude plugin marketplace remove pathways`.

`Parallel-intelligence/pathways-plugin` is public and holds only this built plugin, copied fresh from a reviewed commit (`apps/ui/scripts/release-plugin.mjs`): the method and the code, never client data, and never the client's name, which the tool learns from the admin Worker after sign-in.

## What's in it

| Path | What | Made by |
|---|---|---|
| `skills/pathways/SKILL.md` | What Claude does for `/pathways` | Hand |
| `bin/pathways.mjs` | The tool's commands and local server, with sign-in, fetch, upload and analysis; Node built-ins only (`start`, `stop`, `status`, `check`, `push-structure`, `push-sources`, `push-factors`, `push-dev`, `pull-dev`, `dev-snapshots`, `restore-dev`, `library-plan`, `upload-library`, `rekey-library`) | `apps/ui/standalone/` |
| `app/` | The tool's page, built in standalone mode (no sample data shown) | `apps/ui` |
| `map/` | Christian's map page | `apps/map` |
| `landscape/` | The landscape build, its extraction brief and rules | `packages/landscape` |
| `curation/` | The curate tool: applies the team's decisions in `landscape/decisions/` when the map is built | `packages/curation` |

Don't edit the built parts by hand. After changing the tool, rebuild and commit them:

```bash
pnpm --filter @pathways/ui plugin
```

The tool listens on `127.0.0.1:5180` only and answers this machine's own address. Its log and launch token are in the person's temporary folder (`$TMPDIR/pathways`, or `$TMPDIR/pathways-<port>` on another port through `PATHWAYS_PORT`); the running tool keeps the token file from being cleared. `start` counts a tool already on the port as its own only if it proves it holds that token without being sent it: `/api/ping` answers a fresh random challenge with an HMAC of it and the port under the token, and gives the tool's version. A tool from before 0.9.3 can't, so it gets the token only if lsof and ps show it's the person's own process. An older version of the person's own is replaced, unless it's in the middle of Analyse, Fetch latest or publishing (only a clear "not running" counts as idle). One that can't say, including one whose token file is gone, is left running, and `start` says how to stop it. One started from another Mac account on the same computer is reported, not opened. Stopping signals only a process that lsof shows as the person's own on the tool's address and ps shows as `pathways.mjs serve`. Nothing in this plugin holds client data: documents and what's built from them live in the working folder, outside git.

**The library into the raw bucket** (PAR-312, a one-off for a folder built before the tool): `library-plan [folder]` is a dry run. It matches every document behind the map, and the client's other originals, to its file, label (client, licensed by the publisher list, else public) and the tool's id, with its existing text and chart data, and writes `.pathways-library.json` at the working folder's root, outside the folders push-dev carries. It prints counts only. `upload-library [folder]` plans again and refuses unless that matches the saved dry run (the saved file is never trusted for what to upload or how to label it), then uploads what the raw bucket lacks, in parts above 95 MiB, and stores each document's text (with the converter that made it, never converted again) and chart data beside it. It holds the checkout, stops if a file changed since the plan, and is safe to run again. Labels can't change once uploaded, so the plan needs Cloudflare's licensed list (Fetch latest) first.

**Rekey to the tool's ids** (after upload-library): `rekey-library [folder]` is a dry run printing counts; with `--apply` it moves the folder from the hand-made document ids to the tool's, from `.pathways-library.json` alone. Files named by an old id are renamed; in JSON, ids and finding ids follow, and a file reference follows only when that file was renamed, so links to originals never change. Originals, the text inside text files, backups, scratch, decisions and run logs are never touched. It refuses while any decision exists, backs every file up to `.pathways-rekey-backup/` (outside the synced folders) first, writes `landscape/rekey.json` (old id to new), and plans the library again to check every document comes back under its new id. Rebuild the map after it, then push-dev. The backup holds copies of the client's files: delete it once the version built from them is published.
